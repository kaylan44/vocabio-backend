# Vocabio — Backend architecture

## Overview

Backend of the Vocabio mobile application (French ⇄ Spanish vocabulary quizzes). It started
as a messaging system and now covers three independent features, which share the same server,
the same database and the same authentication:

- **1:1 messaging** between users: conversations, text messages, read indicators, real time
  (REST + Socket.io).
- **Quiz results and statistics**: each quiz finished by a signed-in user is stored in
  detail, and the account page reads aggregated statistics (REST only).
- **Easy Spanish articles**: short news articles written for learners are copied from an
  external site, text and audio, and served to the app (REST only). Off by default, for
  private testing only: see "Articles" below.

The vocabulary itself (words, categories, levels) is not stored here: it lives inside the
mobile app. The backend only stores what users did with it.

## Authentication flow

1. The user signs in through **Google SSO** on Supabase Auth
2. Supabase returns a **signed JWT** containing the `user_id`
3. React Native stores the JWT securely (`expo-secure-store`)
4. Every HTTP request and Socket.io connection includes the JWT in a header
5. The Express server **verifies the JWT** with the Supabase public key (no network call)
6. The user's identity is extracted from the token on every request

## Data model

The source of truth is `prisma/schema.prisma`. The tables below are shown as they
really exist in PostgreSQL (see `prisma/migrations/`).

**Naming pitfall for raw SQL**: Prisma created the tables with the model names
(`"User"`, `"Message"`...) and camelCase columns (`"avatarUrl"`, `"readAt"`...).
PostgreSQL lowercases unquoted identifiers, so the **double quotes are mandatory**:
`SELECT "readAt" FROM "Message"` works, `SELECT readAt FROM Message` fails.

IDs are stored as `TEXT` containing a UUID, not as the native `UUID` type. The UUIDs of
`"Conversation"`, `"Message"`, `"QuizAnswer"` and `"Article"` are generated by the Prisma client
(`@default(uuid())`), not by the database: a raw `INSERT` must provide the `id` itself.
The UUID of `"QuizSession"` is generated by the mobile app (see "Quiz results" below).

### `"User"` table
Synchronized from Supabase Auth by a Postgres trigger on `auth.users` (`sync_auth_users`
migration, which also backfills existing accounts). The lazy upsert in the auth middleware
and the sign-up webhook remain as a safety net.

```sql
"User" (
  "id"         TEXT PRIMARY KEY,  -- same ID as Supabase Auth (JWT "sub")
  "username"   TEXT NOT NULL,
  "avatarUrl"  TEXT,
  "createdAt"  TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP
)
```

### `"Conversation"` table
Represents a 1:1 channel between two users.

```sql
"Conversation" (
  "id"         TEXT PRIMARY KEY,  -- UUID generated by Prisma
  "createdAt"  TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP
)
```

### `"Participant"` table
Join table linking users and conversations.

```sql
"Participant" (
  "conversationId"  TEXT NOT NULL REFERENCES "Conversation"("id"),
  "userId"          TEXT NOT NULL REFERENCES "User"("id"),
  PRIMARY KEY ("conversationId", "userId")
)
```

### `"Message"` table
```sql
"Message" (
  "id"              TEXT PRIMARY KEY,  -- UUID generated by Prisma
  "conversationId"  TEXT NOT NULL REFERENCES "Conversation"("id"),
  "senderId"        TEXT NOT NULL REFERENCES "User"("id"),
  "content"         TEXT NOT NULL,
  "createdAt"       TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
  "readAt"          TIMESTAMP(3)  -- NULL = unread
)
```

### `"QuizSession"` table
One row per quiz finished by a signed-in user (guests persist nothing).

```sql
"QuizSession" (
  "id"         TEXT PRIMARY KEY,  -- UUID generated by the CLIENT (idempotency key)
  "userId"     TEXT NOT NULL REFERENCES "User"("id"),
  "mode"       TEXT NOT NULL,     -- 'fr-es' | 'es-fr'
  "score"      INTEGER NOT NULL,  -- number of correct answers, computed by the server
  "total"      INTEGER NOT NULL,  -- number of questions, computed by the server
  "createdAt"  TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP
)
-- INDEX ("userId", "createdAt")
```

### `"QuizAnswer"` table
One row per question of a quiz session. The vocabulary lives inside the mobile app, so
`"wordId"` is an opaque string and `"category"` / `"level"` are copied onto each answer
(the backend has no word table to join on).

```sql
"QuizAnswer" (
  "id"         TEXT PRIMARY KEY,  -- UUID generated by Prisma
  "sessionId"  TEXT NOT NULL REFERENCES "QuizSession"("id") ON DELETE CASCADE,
  "position"   INTEGER NOT NULL,  -- 0-based order of the question in the quiz
  "wordId"     TEXT NOT NULL,     -- e.g. 'n001'
  "category"   TEXT NOT NULL,     -- noun | verb | adjective | adverb | expression | pronoun
  "level"      TEXT NOT NULL,     -- A1 | A2 | B1 | B2 | C1
  "isCorrect"  BOOLEAN NOT NULL,
  UNIQUE ("sessionId", "position")
)
```

`mode`, `category` and `level` are `TEXT`, not database enums: the allowed values are
defined in `src/services/quizService.ts` and checked by the route. Adding a value to the
mobile app requires deploying the backend **first**, otherwise the result is rejected (400).

### `"Article"` table
One row per article copied from the external source. Written by the sync job only, never
through the API.

```sql
"Article" (
  "id"                TEXT PRIMARY KEY,  -- UUID generated by Prisma, the only id the app sees
  "source"            TEXT NOT NULL,     -- 'holaquepasa'
  "externalId"        TEXT NOT NULL,     -- post id at the source, e.g. '74003'
  "lang"              TEXT NOT NULL,     -- 'es'
  "level"             TEXT,              -- 'easy' | 'intermediate' | NULL = unknown
  "title"             TEXT NOT NULL,
  "excerpt"           TEXT NOT NULL,     -- beginning of the text, for the list
  "content"           JSONB NOT NULL,    -- paragraphs of text segments, never HTML
  "url"               TEXT NOT NULL,     -- original article (attribution)
  "imageUrl"          TEXT,              -- served by the source, not copied
  "audioSourceUrl"    TEXT,              -- internal: where the MP3 was found
  "audioDurationSec"  INTEGER,
  "publishedAt"       TIMESTAMP(3) NOT NULL,
  "createdAt"         TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE ("source", "externalId")        -- an article cannot be stored twice
)
-- INDEX ("publishedAt")
```

### `"ArticleAudio"` table
The MP3 reading of an article, stored in the database. It is a separate table so that no
query on `"Article"` can load megabytes of audio by mistake.

```sql
"ArticleAudio" (
  "articleId"  TEXT PRIMARY KEY REFERENCES "Article"("id") ON DELETE CASCADE,
  "data"       BYTEA NOT NULL,    -- the file itself, about 2 MB
  "mimeType"   TEXT NOT NULL,     -- 'audio/mpeg'
  "size"       INTEGER NOT NULL   -- bytes
)
```

## REST API (Express)

### Auth
All endpoints require the `Authorization: Bearer <JWT>` header, except the two
listed under "Endpoints without JWT" below.

### Endpoints

| Feature | Method | Route | Description |
|---|---|---|---|
| Messaging | `GET` | `/users` | List users (except yourself), sorted by username, 100 max |
| Messaging | `GET` | `/users/search?q=` | Search for a user by username |
| Messaging | `POST` | `/conversations` | Create or fetch a 1:1 conversation |
| Messaging | `GET` | `/conversations` | List the user's conversations |
| Messaging | `GET` | `/conversations/:id/messages` | Paginated message history |
| Messaging | `POST` | `/conversations/:id/messages` | Send a message (fallback without WebSocket) |
| Messaging | `PATCH` | `/conversations/:id/read` | Mark all received messages of the conversation as read |
| Quiz | `POST` | `/quiz-sessions` | Store the result of a finished quiz |
| Quiz | `GET` | `/quiz-sessions/stats` | Aggregated quiz statistics of the signed-in user |
| Articles | `GET` | `/articles` | Paginated list of articles, newest first, without their text |
| Articles | `GET` | `/articles/:id` | One article with its text |
| Articles | `GET` | `/articles/:id/audio` | The MP3 reading of the article |

### Quiz results

`POST /quiz-sessions` body:

```json
{
  "id": "3f2b1c7e-8a54-4d2f-9b1a-0c5d6e7f8a90",
  "mode": "fr-es",
  "answers": [
    { "wordId": "n001", "category": "noun", "level": "A1", "isCorrect": true },
    { "wordId": "v042", "category": "verb", "level": "A2", "isCorrect": false }
  ]
}
```

Returns `{ id, mode, score, total, createdAt }`. `answers` holds 1 to 50 items, in the order
the questions were asked. The client never sends the score: it is computed from the answers.

| Status | Meaning |
|---|---|
| `201` | Session created |
| `200` | Same `id` already stored by this user: nothing is written, the stored session is returned |
| `400` | Invalid body (`{ error }` explains which field) |
| `409` | The `id` is already used by another user |
| `429` | The user created another session less than 10 seconds ago |

- **Idempotency**: the `id` is a UUID generated by the app. Sending the same quiz again
  (network retry) is safe and is not counted by the rate limit. A replay with the same `id`
  but a different content is ignored: the first version stored wins.
- **Rate limit**: one new session per user every 10 seconds. The app must not retry a `429`
  in a loop.
- **Trusted client**: the vocabulary lives in the app, so the backend cannot check that an
  answer was really correct. A user can only falsify their own statistics.

`GET /quiz-sessions/stats` response:

```jsonc
{
  "totalSessions": 12,
  "totalAnswers": 120,
  "totalCorrect": 93,
  "accuracy": 0.775,                 // 3 decimals; null when there is no answer yet
  "lastSessionAt": "2026-10-01T10:00:00.000Z",  // null when there is no session
  "byMode":     [{ "mode": "fr-es", "sessions": 7, "answers": 70, "correct": 55, "accuracy": 0.786 }],
  "byCategory": [{ "category": "noun", "answers": 40, "correct": 33, "accuracy": 0.825 }],
  "byLevel":    [{ "level": "A1", "answers": 80, "correct": 70, "accuracy": 0.875 }],
  "mostMissedWords": [{ "wordId": "v042", "wrong": 4 }]   // 10 max, all time
}
```

`mostMissedWords` only contains word ids: the app resolves them to the actual words.

### Articles

Short news articles in easy Spanish, copied from [Hola Qué Pasa](https://holaquepasa.com)
through its public WordPress REST API. Read-only for the app, and the same for every
signed-in user.

> **Private testing only.** The source publishes no reuse licence. Copying its text and
> audio is acceptable for a private test, not for an app open to other people: ask the
> publisher first. This is why the sync is off by default.

**Configuration.** `ARTICLES_SYNC_ENABLED="true"` turns the sync on (only this exact value;
anything else leaves it off). Without it, the routes work but the tables stay empty.

**Sync job** (`src/jobs/articleScheduler.ts` → `src/services/articleIngestService.ts`):
an in-process timer runs 30 seconds after the server starts, then every 6 hours. Each run:

1. asks the source for its 10 latest news posts (one request);
2. stores the ones not stored yet, each with its MP3 (downloaded one at a time);
3. retries the MP3 of articles stored earlier without audio;
4. deletes the articles published more than 30 days ago, audio included.

An article already stored is never downloaded again, and its text is not refreshed if the
source edits it. If the source cannot be reached the run stops and deletes nothing. Every
URL found in the source's content is checked (https, host `holaquepasa.com`) before being
stored or fetched; the MP3 download also refuses redirects, non-audio types and files over
10 MB.

`GET /articles?level=easy&offset=0&limit=20` response:

```jsonc
{
  "articles": [
    {
      "id": "3f2b1c7e-8a54-4d2f-9b1a-0c5d6e7f8a90",
      "source": "holaquepasa",
      "lang": "es",
      "level": "easy",                  // easy | intermediate | null
      "title": "…",
      "excerpt": "…",                   // about 200 characters
      "url": "https://holaquepasa.com/…",   // original article, for attribution
      "imageUrl": "https://holaquepasa.com/…jpg",   // or null; served by the source
      "publishedAt": "2026-10-03T12:00:00.000Z",
      "audioDurationSec": 232,          // or null
      "hasAudio": true                  // false: do not call the audio route
    }
  ],
  "pagination": { "offset": 0, "limit": 20, "count": 1 }
}
```

- `level` is optional; an unknown value answers `400` (it is not ignored).
- `limit` goes from 1 to 50 (default 20). Unreadable `offset` / `limit` fall back to the
  defaults, like on the messages route.

`GET /articles/:id` returns the same object plus `content`, the text as a list of
paragraphs. Each paragraph is a list of segments; a segment with a `gloss` is a phrase the
source explains, **in English**:

```jsonc
"content": [
  {
    "type": "paragraph",
    "segments": [
      { "text": "El gato vive en " },
      { "text": "una casa pequeña", "gloss": "a small house" },
      { "text": "." }
    ]
  }
]
```

Concatenating the `text` of the segments gives the paragraph. The text is plain text, never
HTML: render it as text.

`GET /articles/:id/audio` returns the whole MP3 (`Content-Type: audio/mpeg`,
`Content-Length`, `Cache-Control: private, max-age=86400`). There is no `Range` support:
the app downloads the file with its JWT, then plays and seeks in its local copy. An audio
element pointed directly at this URL would not work on web, because it cannot send the
`Authorization` header.

| Status | Meaning |
|---|---|
| `200` | Success |
| `400` | `id` is not a UUID, or unknown `level` |
| `404` | No article with this id, or (audio route) the article has no audio |

### Endpoints without JWT

| Method | Route | Protection | Description |
|---|---|---|---|
| `GET` | `/health` | None (public) | Health check used by Railway, returns `{ status, timestamp }` |
| `POST` | `/webhooks/auth` | HMAC-SHA256 signature in the `x-supabase-signature` header (`SUPABASE_WEBHOOK_SECRET`) | Supabase Auth sign-up webhook: creates the user in the database |

## Socket.io events (real time)

Real time is used by messaging only. Quiz results and articles go through REST and emit no event.

### Connection
The client authenticates on connection by passing the JWT:
```js
const socket = io(SERVER_URL, {
  auth: { token: supabaseJWT }
})
```

### Client → server events

| Event | Payload | Description |
|---|---|---|
| `join_conversation` | `{ conversationId }` | Join a conversation's room |
| `send_message` | `{ conversationId, content }` | Send a message |
| `mark_read` | `{ conversationId }` | Mark all received messages of the conversation as read |
| `typing` | `{ conversationId }` | Typing indicator |

### Server → client events

On connection, each socket automatically joins its personal room `user:<id>`.
`new_message` and `message_read` are emitted to the conversation room **and** to the
participants' personal rooms: a client therefore receives new messages from all its
conversations without having to join them. `user_typing` stays limited to the conversation room.

| Event | Payload | Description |
|---|---|---|
| `new_message` | `{ id, conversationId, senderId, sender, content, createdAt, readAt }` | New message (including the ones you sent yourself) |
| `message_read` | `{ conversationId, readAt, readByUserId }` | Messages of the conversation read by `readByUserId` |
| `user_typing` | `{ conversationId, userId, username }` | A user is typing |

### CORS

Calls from a browser (Expo web) require the origin to be listed in
`CORS_ORIGINS` (comma-separated list, default `https://vocabio.vercel.app`).
A defined value replaces the default: to also allow local dev, use
`CORS_ORIGINS="http://localhost:8081,https://vocabio.vercel.app"`.
The same list applies to REST routes and to Socket.io.

## Security

- All endpoints verify the Supabase JWT before processing, except `/health` (public)
  and `/webhooks/auth` (HMAC signature instead)
- Server-side check that the user is indeed a **participant** of the conversation before any access to messages
- The JWT is verified locally (Supabase public key) — no network call to Supabase on each request
- Messages are only accessible to the participants of the conversation
- Quiz results are always written and read for the user of the JWT (`req.user.id`), never
  for a user id taken from the body or the URL
- Articles are fetched by a server-side job only: no request from a client can change what
  is fetched or from where. URLs found in the remote content are restricted to the source's
  host over https before being stored or downloaded, and the text is stored as plain text
- **RLS enabled with no policy** on all `public` tables (`enable_rls` migration):
  the Supabase Data API (PostgREST, `anon` key) has no access to them, the mobile app
  only goes through this backend. Prisma connects as `postgres` (owner of the tables)
  and is therefore not subject to RLS. **Any new table must enable RLS in its
  migration** (checked by `tests/prisma/rls.test.ts`).

## Continuous integration

GitHub Actions workflow: `.github/workflows/ci.yml`.

- **Trigger**: every Pull Request targeting `main` (when it is opened, then on
  each push to its branch). A push on a branch without a PR runs nothing.
- **Steps**: `npm ci` → `npx prisma generate` → `npx tsc --noEmit` → `npm test`, on Node 24.
- **No secrets**: every test mocks Prisma and the auth middleware, so the
  workflow needs neither a database nor Supabase keys.
- **Not covered**: deployment (handled by Railway) and integration tests against a real database.

## Out of scope (V1)

Messaging:

- Group messages (> 2 participants)
- File / image sharing
- End-to-end encryption
- Deleting / editing messages
- Message reactions

Quiz results:

- History endpoint (list of past sessions): only the aggregated summary is exposed
- Quiz duration and the option chosen for a wrong answer: not sent by the app
- Server-side check that an answer was really correct: the vocabulary lives in the app
- Results of guests (not signed in): nothing is stored without a JWT

Articles:

- Any use beyond private testing: the source's content is not licensed for reuse
- A second source, or articles in French (the data model already allows both)
- Refreshing the text of an article already stored
- `Range` requests on the audio, and a file storage instead of the database
- Copying the image: it is loaded from the source by the app
- A manual "sync now" endpoint, and per-user state (read / unread, favourites)
- Integration test against a real database: as for the rest, everything is mocked
